## C. Unknown: only hardware answers (by impact)

The test programs, for the owner's Trinity (lent out now): libxenon programs, results on USB.
- **Harness.** libxenon's `Xe_*` API (`refs/libxenon/libxenon/drivers/xenos/xe.h`) gives render targets
  (`Xe_SetRenderTarget`), textures, shaders from a container (`Xe_LoadShaderFromMemory`), constants, draws
  (`Xe_Draw*`, point, line, triangle, rectangle and quad lists), resolves (`Xe_ResolveInto`) and
  `Xe_Surface_LockRect` to read a surface. Registers it does not wrap (RB_MODECONTROL, PA_CL_CLIP_CNTL bits,
  RB_COLORCONTROL's alpha to mask, PA_SU_LINE_CNTL, VGT_* ...) are written through the ring buffer the way `xe.c`
  does (`Xe_pWriteReg`'s pattern). The display's registers (`DC_LUT_*`, `xenos.c`) are plain MMIO reads and
  writes. libxenon names only the 8_8_8_8, 8, 5551, 565 and 16_16_16_16 formats.
- **Reading exact numbers without a float target:** export them to memory from the shader (`alloc export`, `eA`
  and `eM0`: memexport) and read the guest memory on the CPU after `Xe_Sync`; 32-bit values come out whole.
  Pictures (culling, triangulation, clipping, coverage) use an 8_8_8_8 target and a resolve.
- **Shaders:** microcode assembled with XNA's assembler (`tools/xna`) into the container libxenon loads; words
  XNA will not emit (swizzle 6, odd opcodes) written by hand from `ucode.h`.
- **Judging:** each test has a model in XenoForge (the interpreter `shader_interpreter.cpp`, or a script), so the
  USB file is compared on the PC: the table of mismatches is the result, and any case that agrees with Xenia
  needs no change. One program per group, a header line with the console's GPU revision.

You work on the CPU side of XenoForge (F:\RECOMPs\XenoForge): a lean Xbox 360 system for statically
recompiled games, written from scratch with Xenia (F:\RECOMPs\xenia-canary, BSD) as the reference and
the oracle. The brief says the task and what other agents are touching. Everything below holds for
every such task.

## First

Read CLAUDE.md (Portuguese: the project's rules and the recompiler's tools), docs/recompiler.md (the
design: one description per instruction, the context, floating point, discovery, emission) and
docs/plan.md (A2, A3). The code:
- include/xenoforge/ppc_ops.h: every instruction's semantics, once, for the generated code and the
  interpreter alike; include/xenoforge/ppc_context.h, ppc_generated.h;
- src/ppc.cpp and src/ppc/*.inc: the decoder and disassembler, generated by tools/ppc_gen.py from
  src/ppc/ppc-instructions.xml (Xenia's, unchanged);
- src/ppc_interp.cpp: the interpreter;
- src/recomp_image.cpp, src/recomp_discover.cpp, src/recomp_emit.cpp, include/xenoforge/recomp.h;
- tools/xfrecomp.cpp (analyze, emit, tests), tools/boot.cpp (boot_<game> with the generated code).

## Rules

- One description per instruction: a semantic fix goes in ppc_ops.h and serves both paths. Branches,
  calls and returns are the emitter's (and the interpreter's) own.
- The console wins over Xenia where Xenia's tests (many generated on the console) say so; otherwise
  Xenia is the reference. Code translated from Xenia starts with its BSD notice and is checked against
  its source in the same session.
- rexglue's fork (F:\RECOMPs\rexglue-sdk\src\codegen, BSD, the owner's own fork) and hedge-dev's
  XenonRecomp (F:\RECOMPs\XenonRecomp, MIT) are references for discovery; translated code carries
  their notice. Never XenonRecomp's thirdparty/disasm (GPL). Never modify F:\RECOMPs\rexglue-sdk.
- A wrong discovery guess must cost speed, never correctness: anything uncertain goes through dispatch
  (the interpreter runs what has no generated code). Never build the generated code with -ffast-math
  or -ffp-contract=fast.
- Never put game data in the repo: ISOs, XEX, images, generated code, dumps. Generated code stays under
  F:\RECOMPs\external. F:\RECOMPs\external\gen is the main build's; emit into a directory of your own
  (e.g. F:\RECOMPs\external\gen-<task>\<game>) unless the brief says otherwise.
- English in code, comments, logs and docs. C++20, clang, the repo's .clang-format (4 spaces,
  120 columns). Comments say what the code does and why, in plain prose; no banners.
- Keep Linux and Android (ARM64) open (docs/plan.md, "Hosts"):
  - no Win32 call outside a `_WIN32` branch with a POSIX counterpart, or a stub marked TODO;
  - no x86 intrinsics in what the generated code includes;
  - sizes from the host (page size), never a constant.
- Do not commit. Leave the work uncommitted in your worktree; it is merged by whoever launched you.
- docs/plan.md is kept out of git, so a worktree has none. Read it at F:\RECOMPs\XenoForge\docs\plan.md
  and never edit it. Put the changes your work makes to the plan in your report, as a short list.
- References are downloaded into F:\RECOMPs\refs (index: refs/README.md). Read them there before going
  online.

## Checks

- The instruction tests (assembled in F:\RECOMPs\external\ppc_tests):
  `XF_PPC_TESTS=../external/ppc_tests build/ppc_test [filters] [-v]` (interpreted) and, configured with
  `-DXF_PPC_TESTS_DIR=F:/RECOMPs/external/ppc_tests`, `build/ppc_recompiled_test` (recompiled). Both must
  keep passing everything they pass today.
- The decoder: `build/xfppc <file> <base>` against the oracle F:\RECOMPs\external\oracle\ppc_oracle.exe
  (same format; compare with `cmp`).
- Discovery: `build/xfrecomp analyze <iso> --compare <rexglue's *_init.cpp>` (where
  rexglue's lists are: docs/plan.md, "Test discs"). Explain the differences by kind.
- The games run: `build/xfrecomp emit <iso> <dir>/<game>`, configure with
  `-DXF_GAMES=<game> -DXF_GEN_DIR=<dir>` and build `boot_<game>` (the generated code takes several
  minutes; long tool timeouts). `boot_<game> <iso> --seconds 20` prints the swaps per second and the
  addresses the interpreter was entered at, most first: what discovery missed. `--interpret` runs the
  same binary without the generated code, to tell a recompiler bug from a kernel one.
- The ISOs: F:\RECOMPs\XenoForge\docs\plan.md, "Test discs" (local only, read from the main checkout).

## Build and tests

- Build: `cmake -S . -B build -G Ninja -DCMAKE_C_COMPILER=clang -DCMAKE_CXX_COMPILER=clang++` (in a
  worktree also `-DSTB_DIR=F:/RECOMPs/xenia-canary/third_party/stb`), then `cmake --build build`, then
  `ctest --test-dir build --timeout 300`. Everything must pass. Other agents build on the same machine,
  so builds can be slow.
- Run every test, tool and boot under a timeout (`timeout 300 ...`), and never leave a process running
  when you finish.
- Shell: Bash is Git Bash on Windows. Heredocs mangle backslashes, so make code changes with
  Edit/Write.

## No game names (the owner's rule, 2026-11-08)

Nothing in the repository names a specific game: no title, codename or port
name in code, comments, tests, CMake, scripts, examples, READMEs, docs or
commit messages. Write "a game", "<game>", "a UE3 game with 4.7M
instructions", made-up addresses in examples. Running real discs by hand to
test is fine; say which ones only in the report to the main session.

## Token economy (the owner's rule, 2026-11-06)

Tokens are the session's budget: every line read stays in the context. Spend them on the work, not on
output.
- **Builds and tests write to a file; read only what matters.** For example:
  `cmake --build build -j 4 > build.log 2>&1; echo $?; grep -E "error|FAILED" build.log | head`. Do
  the same for ctest, boots and replays: the summary lines, the first errors, the counts you need.
- **Big files are read by range, after a search.** Use Grep to find the function, then Read with an
  offset and a limit. Never read a whole large file such as renderer.cpp, shader_translator.cpp, or a
  Xenia source, and never read the same range twice.
- **Repeat a test only as much as the question needs.** Five runs show a test is not flaky. Go further
  only when chasing a hang or a race.
- **Measure once per question.** A run's numbers go in the report; don't rerun to see them again.
- **The report is short:** about 30 lines, the essentials of the list below. Details belong in the docs
  you changed, not in the report.

## Test budget (the owner's rule, 2026-11-06)

Tests serve the work; they never become the work. An agent once spent over half an hour rerunning the
whole replay suite while iterating.
- **While iterating, run the narrowest check:** one test binary, one trace or frame, one test filter, one
  20-30 s boot. The full suite (all of ctest, all of replay_test) runs once at the end, and once more
  only if a fix followed a failure in it.
- **At most 30 minutes of testing in a row** (wall time, builds aside) without a new finding. Past that,
  stop and report what passes, what fails and what is left; whoever launched you decides what next.
- **A run that hangs or passes its timeout is a finding, not something to retry:** kill it, note the
  command and where it stopped, retry at most once; a second hang goes in the report as open.
- **The same failing check gets at most three fix-and-rerun rounds.** Then it goes in the report as open,
  with what was learned.
- Never loop runs to watch a number, and never rerun a suite that passed to confirm it.

## Report

When done, report:
- the files added and changed;
- what changed in the semantics, discovery or emission, and where it differs from Xenia or rexglue;
- the numbers: tests passed, functions against rexglue, boot_<game>'s swaps per second and
  interpreted entries, before and after;
- the test results;
- anything left open.
